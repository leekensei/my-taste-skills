# React 컴포넌트 합성

## 책임 경계 선택

props로 시작한다. 구조를 나누기 전에 현재 코드에서 관찰한 문제를 설명한다. 구조를 통일하고 싶다는 이유만으로 추상화를 추가하지 않는다.

| 현재 겪는 문제 | 검토할 방법 |
| --- | --- |
| 1단계: API가 작고 안정적이다 | props와 로컬 상태를 유지한다. |
| 2단계: 사용하는 쪽에서 기존 API로 표현할 수 없는 배치가 필요하다 | 조립 가능한 하위 컴포넌트를 제공한다. 컴포넌트 자체의 상태는 props로 유지한다. 기본 UI 컴포넌트 내부의 협력에는 비공개 context를 사용할 수 있다. |
| 3단계: 같은 렌더링 구조에 교체 가능한 데이터 출처가 필요하다 | 출처를 모르는 소비 컴포넌트와 작은 계약을 구현하는 provider를 검토한다. 계약에는 `state`, `meta`, `actions` 중 필요한 것만 둔다. |
| 4단계: 액션이 무관한 중간 계층을 통과하거나 형제 컴포넌트에서 같은 상태를 다뤄야 한다 | 참여하는 분기들의 공통 상위에 기능 단위 provider를 둔다. 말단 컴포넌트만 쓰는 상호작용 상태는 로컬에 남긴다. |

데이터 출처와의 연결은 계약 뒤에 숨기고, 말단에서만 필요한 상태는 그 컴포넌트에 둔다. 이름은 프로젝트의 기존 관례를 따른다.

출처: Maxime Grébauval의 [Orus 아티클](https://backstage.orus.eu/react-composition-patterns-at-orus/), 2026-07-15. 원문의 공유 상태 예제는 게시 시점에 구현 방향을 제안한 것으로, 실제 출시된 사례는 아니었다.

## 실제 프로젝트에 적용

다음은 이 스킬에서 추가한 구현 점검 사항이다. 원문 자체의 주장과 구분한다.

- 컴포넌트를 사용하는 코드, 설치된 React 버전, 기존 UI 컴포넌트, 조회 라이브러리와 테스트를 읽는다. 문제를 해결하는 가장 작은 변경을 찾는다. props나 children을 직접 전달하는 것만으로 충분할 수 있다. 정적 데이터로 테스트한다는 이유만으로 context를 도입하지 않는다.
- 사용자가 API 전환을 요청했거나 현재 문제를 해결하는 데 필요한 경우가 아니면 기존 공개 API를 유지한다. 상태의 소유 위치를 옮길 때 비동기 액션의 타입·인자·실패 전파·처리 중 표시·캐시 갱신·상태 초기화 동작을 보존한다.
- 프로젝트가 지원하는 context API를 사용한다. React 18 이하에서는 `Context.Provider`가 필요하다. 예제 문법을 따라 하려고 React를 업그레이드하지 않는다. 필수 기능 context의 provider가 빠졌다면 명확한 오류를 내도록 한다.
- 지연 조회가 필요하면 비활성 패널이 실제로 마운트되는지, 조회 라이브러리가 실행 비활성화나 suspension을 지원하는지 확인한다. `Suspense`로 감싸는 것만으로 이미 마운트된 조회의 요청 시점이 늦춰지지는 않는다. 선택 상태와 재마운트 시 동작을 보존한다.
- 디자인 시스템에서 지원하는 합성 API를 우선한다. HTML 요소의 의미, 키보드 동작, 레이블, ref와 이벤트 처리를 보존하고 상호작용 요소를 중첩하지 않는다. 원문과 모양을 맞추기 위해 렌더링할 요소를 바꾸는 전용 도우미를 새로 만들지 않는다.

React API 참고: [context 버전 호환성](https://react.dev/reference/react/createContext#somecontext-provider), [Suspense](https://react.dev/reference/react/Suspense). 구현이 특정 라이브러리의 동작에 의존할 때만 해당 문서를 추가로 확인한다.

## 검증과 설명

선택한 경계를 구현할 구체적인 예시가 필요하면 [단계별 레퍼런스 안내](references/examples.md)에서 1~4단계 중 해당 예제만 읽는다. 예제의 교육용 API로 기존 코드를 일괄 전환하지 않는다.

경계를 바꿨다면 관련된 사용자 동작을 확인한다. 다른 레이아웃 배치, 네트워크 없는 fixture의 빈 화면, 공유 액션의 결과 반영, 독립적인 로컬 편집 상태, 변경 요청 실패, 탭 선택 전 요청 횟수 등이 대상이다. 프로젝트의 기존 검증 수단을 사용하고, 이 스킬만을 위해 테스트 도구를 새로 도입하지 않는다.

관찰한 문제, 선택한 경계와 검증한 동작을 설명한다. props를 유지한 결정도 포함한다. 실제로 완료한 검증과 제안만 한 검증을 구분한다. 리뷰만 요청받았다면 파일을 수정하지 않고 구체적인 발견 사항과 최소 변경안을 제시한다.
